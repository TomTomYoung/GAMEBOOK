# ゲームシナリオモデルとHTML版の対応

## 1. この実装の範囲

このHTML版は、短編20作と中編3作の番号付き本文を、条件付き選択と公開記録で遊ぶための実行エンジンです。短編には初版・第2版があり、中編は全40章を実装しています。現在の作品数・素材・残作業は[資料案内](README.md)を参照してください。

短編GB01〜GB20の制作モデルは[v1.2](SCENARIO_MODEL_V1_2.md)、中編3作と未実装のGB21〜GB40の制作モデルは[v1.2b](SCENARIO_MODEL_V1_2B.md)です。両モデルの全文をリポジトリに保存しています。中編の原稿変換は[MEDIUM_IMPLEMENTATION.md](MEDIUM_IMPLEMENTATION.md)で説明しています。

モデルの汎用IR雛形をそのまま読み込む仕組みではありません。人物・法則・制度・推論・演出の根拠は作者資料で保持し、プレイ中に必要な条件と効果を `state` と `nodes` へ具体化しています。自由文から新しい行動を自動生成する機能はありません。

23作は独立作品です。作品間で人物、所持品、時間、知識、出来事を共有しません。モデル本文の例にある `adv` の `q001`〜`q020` と、本リポジトリの作品IDも区別します。

## 2. 版番号の意味

- **設計モデルの版**：作者が何を定義し、どう照合するかを定めるv1.2／v1.2bです。中編のv1.2b原稿も既存エンジンの形式へ変換するため、実行データ・保存データの `modelVersion` は `1.2` です。
- **作品の版**：画面で選ぶ初版・第2版です。短編初版は `GB01`、第2版は `GB01-V2` のように別IDで進行と結末を持ちます。
- **作品の内容版**：各作品データの `revision` です。同じ作品IDの改稿を識別し、保存互換を判断します。2026年10月23日現在、短編初版のGB07・GB11〜GB15は1、ほかは2。第2版のGB01-V2は4、ほかは1。中編M01〜M03は1です。
- **実行アダプターの版**：`adapterVersion: 1`。条件の評価、効果の確定、本文変種、再生方法を識別します。
- **保存形式の版**：個別の `gamebook-session` と本棚全体の `gamebook-shelf` は、ともに `version: 1` です。画面の位置・設定と物語の状態を分けて保存します。

素材台帳の `schemaVersion: 1` は、これらとは別の表示素材の形式です。画像の差し替えだけでは作品の内容版を変更しません。ただし、本文にない事実の先取りや現在の状態との食い違いがないか、演出と情報開示を点検します。

セーブの版番号だけを新版へ付け替える移行は行いません。内容が変わった場合は、旧版の選択履歴を検証して移行します。GB01の第2版では旧revision 2・3から現在の4へ履歴を引き継ぐ処理を実装しています。

## 3. 五層の割当て

### World

固定過去、初期状況、法則、制度、実体の所在と保持は `author.facts`、`author.entities`、`author.situation`、`author.mechanism`、`author.institution` が作者用の根拠です。プレイに応じて変わる公開値は `state` の宣言と、セッションの `state` に割り当てます。進行節から一意に決まる位置は節に含め、重複した位置フラグを追加しません。

### Agent

人物の目的、情報源、価値、判断の変化は `author.agents` に保持します。該当経路で必要な知識・約束は公開記録または到達する節で表し、別経路や前回のプレイから持ち込みません。NPCの判断は原稿に定義された有限分岐として再現します。

### Narrative

本文の正本は `setup`、`rules`、各節の `body` と `variants`、選択肢の `label` です。作者用の全台帳をプレイ本文へ自動挿入しません。`author.presentation` が情報を出す順番と、合流後にも残す差の点検箇所を記録します。

### Audience

`hook`、`author.kernel`、選択肢の `why`、`author.presentation` で、読者が選択時点に知り得ることと、その時点で選べる理由を整理しています。現実の読者が理解した内容をエンジンが測定できるとは仮定しません。本文のページ番号や読書履歴を、人物の真相理解フラグへ変換しません。

### Transformation / Reveal

世界への変化は選択の `effects`、その出来事の意味は `event` と作者用の根拠、経路で変わる提示は `variants` で保持します。文章の再解釈だけで固定過去や消費済み資源を変えません。巻戻しを含むGB15では、作品内に定義した巻戻し選択だけが、宣言された範囲を復元します。

## 4. 九つの追加検査要求との対応

### V12-SITUATION — 通常運用と依頼成立

`author.situation` と `author.facts` を根拠に、`setup` と冒頭の節で依頼と介入範囲を示します。例えば [GB01](../data/stories/gb01.json) は、二名の局員が運搬できない事情と救助舟への連絡を定義し、運搬人を頼む理由を示しています。UIは本文の前提を省略せず、作品を始める際に導入と規則を読めるようにします。

### V12-MECHANISM — 原因、費用、作用、結果

`author.mechanism` と法則の事実項に、作用の範囲と時間・数量の根拠があります。実行に必要な部分を `when` と `effects` に限定して記述します。[GB05](../data/stories/gb05.json) の雲から瓶への移し替えを減量と混同せず、[GB14](../data/stories/gb14.json) の一巡の世話と自然冷却を選択の更新としてまとめます。画面を開いたままの現実時間では数値を減らしません。

### V12-GOAL — 人物の目的の発生と変化

目的が変わるきっかけと本人の情報は `author.agents`、該当節の出来事と会話にあります。汎用的な「友好度」を後付けせず、作品が必要とする差だけを記録します。[GB01](../data/stories/gb01.json) のカヨの仕分けの希望は、実際に舟着場へ運ばれた後の節にあります。未救出経路へその会話を表示しません。

### V12-INSTITUTION — 権限と効力

`author.institution`、制度の事実項、選択の `event` が、同意・記録・権限・引渡しの関係を支えます。[GB03](../data/stories/gb03.json) の箱の所有者と預け主、[GB08](../data/stories/gb08.json) の仮移送と留置解除、[GB20](../data/stories/gb20.json) の錨の所有と店内保持を同じ状態に潰しません。本文中の制度は各作品内の創作制度として扱います。

### V12-INFERENCE — 証拠が支える範囲

`author.inference`、手掛かりに対応する記録、節と本文変種で、観測と断定の範囲を分けます。[GB11](../data/stories/gb11.json) では古い案内帳が現在の水深まで証明することはなく、[GB19](../data/stories/gb19.json) では見えた姿の数と本人の身体の受入を区別します。画面に人物名や結末名が存在することを、その人物の知識として扱いません。

### V12-RESOLUTION — 提案から実行・確認へ

`author.resolution` と節ごとの `event` が、同意、資源、担当、移動、作業、確認を定義しています。実行側は選択の成功効果を確定してから、到着先の本文を表示します。[GB18](../data/stories/gb18.json) では出演の相談と水路作業、実際の温石と作業代の引渡しを分けています。終端の `requires` が成立していない結末を成功として受理しません。

### V12-ALTERNATIVE — 代案と非介入

`author.alternatives` と実際の選択肢を対応させます。[GB05](../data/stories/gb05.json) の音が届かない場所で最後の鐘を待つ案、[GB17](../data/stories/gb17.json) の安全に整備係を待つ案や原稿を丸める案は、原稿に含まれた実行可能な分岐です。UIが特定の結末だけを正解として強調し、別の有効な代案を隠すことはしません。

### V12-CHOICE — 選択時点の意図と作用

選択の `label` は引き受ける行為、`when` は実行条件、`effects` は公開値の変更、`why` はその時点で選べる理由、`event` は確定する出来事の作者用説明です。条件は表示時だけでなく確定時にも照合します。読み返し、ページ送り、作品を開き直すことを選択確定として数えません。

### V12-ASSUMPTION — 追加設定の範囲と提示

`author.facts` の事実種別と本文、`author.support_links`、`author.presentation`、`author.review_focus`、`author.applicability` に、今回の創作、適用範囲、依存先、照合点があります。人物・法則を画像の都合で新しく追加する場合も、この根拠を先に確認します。素材は作者だけが知る真相を表紙で公開せず、状態によって違うものを一枚の挿絵で断定しないようにします。

九つの契約は名前を並べただけで充足したと判断できるものではありません。自由文の人物・制度・因果の照合は原稿レビューに属し、HTMLエンジンの型検査や全状態探索によって自動証明された意味の整合性とは区別します。

## 5. 作品データと実行規則

短編初版の正本は `data/stories/gbNN.json`、第2版は `data/editions/gbNN-v2.json`、中編は `doc/drafts/mediumNN/` の章別Markdownです。ブラウザは生成済みの `js/stories.js`・`js/editions.js`・`js/medium.js` を利用します。`fetch`、ES Modules、CDN、ゲーム用のビルド手順に依存しないため、作品を遊ぶ入口は配布フォルダの `index.html` です。

### 状態宣言

`state` は次の三種類です。

- `bool`：真偽値。文字列の `"true"` を真偽値へ暗黙変換しません。
- `int`：`min`〜`max` の整数。範囲外や小数を受理しません。
- `enum`：`values` に列挙した文字列のいずれか。

各項目には `id`、日本語の `label`、`initial`、`meaning` があり、セッションは宣言された項目だけを持ちます。GB19の状態宣言は空配列です。必要な進行差が節に含まれているため、便宜的な数値やフラグを増やしません。

### 条件

`when`、`variants[].when`、`ending.requires` は述語配列で、同じ配列内はANDです。演算子は `eq`、`ne`、`gt`、`gte`、`lt`、`lte` です。空の条件配列は成立します。異なる代替経路は、個別の選択肢や本文変種として定義されています。

コード文字列を実行する `eval` は使用しません。未定義の変数・演算子・参照先を、都合のよい条件に読み替えません。

### 効果と本文

`effects` の演算子は `set` と `add` です。選択確定時は現在の節と条件を確認し、変更後の状態を検査して、一つの遷移として確定します。到着しただけで別の効果を発生させる入口処理はありません。

到着節の `body` に、条件が成立する `variants` を原稿の順番で**すべて**加えます。最初の一致だけを採用する処理ではありません。中編の `whenBefore` は直前の選択より前の状態で評価し、通常の `when` は到着後の状態で評価します。必要な前の状態は選択履歴から再生します。本文のページを何度読んでも、所持品、時間、知識、約束、受入済みの人員は増減しません。

節IDの再登場だけで異常な循環とは判断しません。GB14の巡回、GB15の一度の巻戻し、GB20の任意順の来客対応では、節と現在状態の組で進行を区別します。

### 結末

`ending` がある節が終端です。結末の `requires` が成立することを確認してから、その結末の経験を収集記録へ登録します。収集済みの結末は次のプレイの資源や知識になりません。結末IDの番号に優劣を付けません。

## 6. 保存と再開

個別セッションの形は次のとおりです。これは構造を説明する例で、実際の `state` は該当作品の宣言と一致します。

```json
{
  "format": "gamebook-session",
  "version": 1,
  "modelVersion": "1.2",
  "adapterVersion": 1,
  "storyId": "GB01",
  "contentRevision": 2,
  "nodeId": "01",
  "state": {
    "tide": 4,
    "kayo": false,
    "newmail": false,
    "oldmail": false
  },
  "trail": []
}
```

`trail` は選択したIDを順に保存した配列です。取込時は初期状態からこの履歴を再生し、保存された節と全状態が一致するか確かめます。自己申告された現在の所持品や結末だけを信用して読み込みません。履歴は最大1,000選択とし、壊れた参照や極端な入力を拒否します。

本棚全体には作品別セッション、結末に至った履歴、本文の栞、表示設定、開いていた作品IDを保存します。結末収集の取込も、保存された履歴を再生して実際に該当結末へ到達することを確認します。栞は `intro`、本文の `page`、`nodeId`、`trailLength` を使う画面の位置で、現在のセッションとの一致を確かめます。導入の栞は選択履歴がまだ空のときだけ有効です。栞を変えても物語の状態は変わりません。

本棚の検証は `js/storage.js` の `GBStorage` が担当します。文字サイズは18・20・22・24、テーマは `day` または `night` の宣言値に限定し、未定義の保存キーや互換性のない版を黙って補修しません。取込は本棚全体を検証してから反映し、一部だけを混ぜた不整合な状態を作りません。ファイル取込の上限は2MBです。

自動保存とセーブファイルの入出力は、本棚の持続と持運びを担当します。ブラウザの保存領域を利用できない場合もプレイ中の状態は保持し、セーブファイルへ書き出せるようにします。ファイルの置き場所やブラウザを変えた際に、別の保存領域になる可能性があるため、移動は書出したセーブファイルを使う手順にします。

## 7. 一画面に収める読書UI

本文、選択肢、記録、画面上部の操作を、それぞれ高さの決まる領域へ配置します。本文が長い場合は実際の表示領域と文字組みに合わせてページに分け、本文の直後へ操作欄を積み重ねて画面外へ追い出す構成を避けます。文字サイズや画面サイズを変えた場合は、本文を再分割します。

作品一覧はページを切り替えて23作を探せる構成です。短編・中編の絞込みと検索があり、全作品のカードを縦に積んでページ全体を長くしません。規則、履歴など長い参照情報は、範囲を定めた画面内の表示で読めるようにします。これらの参照表示にある内部スクロールと、ゲーム本体が下方へ伸び続けることは区別します。

画像は本文と選択を支える飾りとして扱います。通常の読書画面では横長の小さな挿絵を節見出し付近に置き、狭い画面では本文と操作の面積を優先して省略できます。画像が非表示でも、選択に必要な情報はすべて文章に残ります。音楽もオフのままで作品の判断と結末は完全に理解できます。

## 8. 検査の区分と改稿時の確認

原稿制作時の確認は [SOURCE_REVIEW.md](SOURCE_REVIEW.md) に残しています。HTML版の実行試験と混ぜて報告しません。現在のコードに対する単体試験は `npm test` で行います。確認済みの件数とブラウザ試験は[VALIDATION.md](VALIDATION.md)を参照してください。

実行側では、全作品の参照・型・条件・効果・終端、到達可能な状態と選択、数量の境界、再生と保存の往復を点検します。ブラウザでは、実際の選択、連続操作、再読、再起動、セーブの出入と、机上の数値計算では分からない本文と操作欄の収まりを確認します。1366×768、1280×720、390×844、360×640などは、画面の大小を比較する確認例です。実施していないサイズを検証済みとして扱いません。

改稿時は次の順に進めます。

1. [資料案内](README.md)で作品と版に対応する正本を確認し、根拠・本文・条件・効果・結末を一緒に見直す。
2. `revision` と保存互換の扱いを決め、変更前の検査結果をそのまま新版の証明として使わない。
3. `node scripts/build-data.cjs` でブラウザ用データを再生成する。
4. 自動試験を実行し、変更した経路・合流・終端を実際の画面でも遊ぶ。
5. 意味や情報開示が変わる改稿は、本文だけを読む視点と、作者用根拠を参照する視点の両方でレビューする。

この実装には、ランダムな本文生成、汎用戦闘シミュレーション、自由入力の推理判定、外部AI呼出し、クラウドへのセーブ同期は含めません。収録23作に必要な動作は、明示された選択、公開状態、本文変種、有限の結末で扱います。
